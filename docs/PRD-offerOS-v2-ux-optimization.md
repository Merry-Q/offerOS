# OfferOS v2 用户体验优化 PRD

> 版本：v2.0  
> 状态：待评审  
> 依据：`docs/offerOS-improvement-strategy.md` 与当前代码实现  
> 目标版本：OfferOS v2  
> 核心主题：从“功能集合”升级为“推动用户完成投递的求职工作台”

---

## 1. Summary

OfferOS 已经实现批量匹配、链接抽岗、自动选简历、求职偏好、跨简历证据池、投递状态、公司视图和故事库。当前主要问题不再是功能缺失，而是各功能仍以独立模块呈现，用户完成一次真实投递时需要自己判断下一步。

v2 不扩张岗位供给或增加重型功能，重点重构“导入岗位 → 快速决策 → 修改简历 → 投递 → 面试准备”的体验，使系统从匹配报告工具变成能持续推动行动的专属求职顾问。

## 3. Background

### 3.1 产品现状

现有产品已具备：

- 单岗 JD 文本/截图导入、解析、判分和六模块报告。
- 批量粘贴 JD、网页链接抽岗、预览编辑和批量判分。
- 按岗位自动推荐简历。
- 匹配库公司、岗位、地区、招聘类型和投递状态筛选。
- 原岗位链接回跳、星标、深报告生成。
- 求职偏好、跨简历取材、故事库和公司视图。

现有能力已经覆盖原策略 Phase 1–4 的主要产品项。因此，继续横向添加功能的边际价值较低。

### 3.2 当前体验问题

| 问题 | 当前表现 | 用户影响 | 为什么现在优化 |
|---|---|---|---|
| 首页与产品目标错位 | 默认进入单岗 JD 匹配 | 用户仍把产品理解为单岗报告机 | 核心目标已变为“多评少深”和投递推进 |
| 功能之间断裂 | 批量匹配、报告、匹配库、状态分属不同页面 | 用户完成判分后需要自己找下一步 | 能力齐全后，串联能力比新增能力更重要 |
| 结果页操作过多 | 星标、报告、详情、投递链接并列 | 决策负担高，不知道哪个动作最重要 | 判分结果应该直接转化为行动 |
| 导入规则不自然 | 批量文本依赖 `---` 或空行切分 | 容易误拆，用户需学习系统规则 | 导入是高频入口，摩擦会直接降低使用频次 |
| “匹配库”偏系统语言 | 以岗位历史和版本为主要组织方式 | 用户难以看到当前有哪些岗位需要处理 | 求职者更关心“待改、待投、已投、面试中” |
| 报告重展示、轻执行 | 六个模块通过 Tab 平铺 | 内容完整，但用户还要自己归纳要做什么 | 报告价值应体现在改得动、面得赢 |
| 顾问解释不足 | 推荐简历有结果，但比较和纠错入口弱 | 推荐错误会迅速损伤信任 | “推荐默认、人可改”需要被交互真正落实 |
| 缺少全链路反馈 | 有部分后台事件，但缺少 v2 漏斗 | 无法判断用户卡在决策还是行动 | v2 的目标必须从功能使用切到任务完成 |

### 3.3 Why now

1. 原策略中的关键能力已完成，具备重组为完整用户旅程的基础。
2. 当前最关键的验证不再是“功能能否实现”，而是“用户是否会从判分继续推进到投递”。
3. 如果继续添加公司分析、故事库等功能，会增加导航和认知负担，反而削弱主路径。

## 4. Objective

### 4.1 产品目标

让用户打开 OfferOS 后，无需理解内部模块，也能明确知道：

1. 今天有哪些岗位值得处理。
2. 每个岗位下一步做什么。
3. 如何使用最合适的简历完成投递。
4. 投递后如何准备面试。

### 4.2 北极星指标

**高意向岗位推进完成率**

定义：

```text
在统计周期内，从“建议投/用户保留”的岗位中，
完成至少一次有效推进动作的岗位数
÷ 建议投/用户保留的岗位总数
```

有效推进动作包括：生成行动报告、应用简历建议、进入待投、点击原岗位链接、标记已投、进入面试中。

### 4.3 Key Results

以下为上线后首个完整观察周期的目标，基线需在开发前补采：

| KR | 指标目标 |
|---|---|
| KR1 | 新用户首次完成一个岗位决策的中位时间 ≤ 10 分钟 |
| KR2 | 批量判分完成后，有效推进率 ≥ 50% |
| KR3 | “建议投”岗位进入“待投/已投”的转化率较 v1 提升 30% |
| KR4 | 自动推荐简历的采纳率 ≥ 60%，且用户能查看推荐原因 |
| KR5 | 链接或文本导入后，无需返工即可判分的岗位占比 ≥ 85% |
| KR6 | 行动报告完成后，至少执行一次“应用建议/复制内容/进入待投”的比例 ≥ 40% |

### 4.4 护栏指标

- 单岗和批量 Judge 结果质量不得下降。
- 深报告继续使用同一质量契约，不制作缩水版报告。
- 不建议投的比例不得因推进指标而被人为压低。
- 推荐简历允许修改，修改后不得丢失已导入 JD。
- 不以增加投递数量作为唯一成功标准。

## 5. Market Segments

### 5.1 核心用户

**多岗位集中筛选者**

- 晚上集中浏览 Boss、官网、内推群等来源。
- 一次处理 5–20 个岗位。
- 主要任务是快速判断哪些值得投，再深耕少数岗位。

**多方向或转岗用户**

- 有多份简历，不确定每个岗位该用哪一版。
- 需要跨简历复用真实经历。
- 害怕选错简历或为了匹配而编造经历。

**进入投递和面试阶段的用户**

- 已经有高意向岗位。
- 需要明确修改项、投递入口和面试准备内容。
- 不希望维护复杂 CRM。

### 5.2 用户约束

- JD 可能来自登录墙、截图、聊天记录或不规范网页。
- 用户通常时间有限，不愿填写完整职业规划表单。
- 用户对 AI 推荐信任有限，需要理由和修改权。
- 岗位链接可能失效，元数据可能缺失。
- 用户在桌面端做深度处理，也可能从移动端复制链接。

## 6. Value Propositions

| 用户任务 | v1 体验 | v2 价值 |
|---|---|---|
| 快速筛选多个岗位 | 能批量判分，但结果后续动作分散 | 按建议排序，并直接给出下一步 |
| 决定用哪份简历 | 给出推荐结果 | 给出推荐、比较理由和纠错入口 |
| 推动岗位进入投递 | 需要去匹配库手动改状态 | 系统按岗位状态持续提示行动 |
| 修改简历 | 阅读六模块后自行提炼 | 先展示必须修改项，并支持应用/写回 |
| 准备面试 | 在报告 Tab 中查看 | 自动形成岗位面试任务清单 |
| 管理求职进度 | 通过筛选查看历史岗位 | 以待决策、待改、待投、已投、面试中组织 |

核心差异保持不变：

- 独立判断，敢于给出“不建议投”。
- 解释匹配依据，不做黑盒推荐。
- 支持任意来源 JD，不替代招聘平台。
- 多简历和跨岗位证据复用。
- 先筛后深，减少无效时间投入。

## 7. Solution

### 7.1 v2 信息架构

导航调整为：

1. **今日工作台**：默认首页，集中展示任务、进度和快捷导入。
2. **导入岗位**：批量导入为默认模式，单岗精细分析为次级模式。
3. **投递看板**：替代“匹配库”作为用户侧名称。
4. **个人资产**：整合求职偏好、简历库和经历故事库。

六模块报告不再占一级导航，作为岗位详情的一部分。

管理端入口仅对管理员展示，不在普通用户主导航中出现。

### 7.2 核心用户流程

```text
今日工作台
  ↓
粘贴链接 / JD / 截图
  ↓
系统识别岗位并让用户确认
  ↓
批量判分 + 自动选择简历
  ↓
结果按“建议行动”排序
  ├─ 不建议投 → 归档/保留观察
  ├─ 待补证据 → 优化简历
  ├─ 可以投 → 去投递
  └─ 已投递 → 准备面试
  ↓
投递看板持续推进
```

### 7.3 优化项一：今日求职工作台

#### 7.3.1 为什么优化

当前首页默认是单岗 JD 匹配，与“单位时间完成多岗决策”的产品目标不一致。用户每次进入产品都要先判断去批量页、匹配库还是报告页，系统没有告诉用户最值得处理的事项。

#### 7.3.2 具体落地方案

首页包含四个区域：

**A. 主行动入口**

- 主按钮：“导入今天看到的岗位”。
- 支持直接粘贴链接、JD 文本或截图。
- 次按钮：“精细分析一个岗位”。

**B. 今日任务**

按优先级最多展示 5 条：

1. 报告已经完成，等待查看。
2. 高分岗位仍未进入待投。
3. 待改简历岗位尚未处理。
4. 已投岗位尚未准备面试。
5. 导入失败或信息不完整的岗位。

每条任务只提供一个主按钮，例如“查看修改项”“去投递”“开始备面”。

**C. 求职进度**

展示当前周期：

- 已导入岗位数。
- 已完成判分数。
- 建议投岗位数。
- 待投数。
- 已投数。
- 面试中数量。

**D. 继续上次任务**

- 展示最近一个未完成批次或岗位。
- 支持返回原位置，不要求重新导入。

#### 7.3.3 技术开发要求

- 新增工作台聚合接口，例如 `GET /api/dashboard`。
- 后端返回统计值、待办任务和最近任务，不由前端多接口拼装。
- 待办优先级由固定规则生成，首期不使用 LLM。
- 任务必须携带 `action_type`、`action_label`、`target_id` 和目标页面。
- 支持空状态、新用户状态和任务全部完成状态。
- 聚合查询需按 `user_id` 隔离，建议建立状态、更新时间相关索引。
- 首屏接口目标 P95 ≤ 800ms，不包含 LLM 请求。

#### 7.3.4 验收标准

- 登录后默认进入工作台。
- 用户能在一个页面开始导入或继续未完成任务。
- 每条待办只有一个明显主行动。
- 用户点击任务后能直接到达对应岗位和操作位置。

#### 7.3.5 产品边界

- 不做日历、提醒中心或复杂任务管理。
- 不提供 AI 每日聊天问候。
- 不生成用户未提交的岗位推荐。
- 首期“今日”按自然日展示，进度统计周期允许切换为近 7 天。

### 7.4 优化项二：统一导入与智能切分

#### 7.4.1 为什么优化

当前批量粘贴要求用户用 `---` 或空行分隔。空行本身又常出现在单份 JD 中，容易误拆。网页提取失败时会生成占位文本，用户仍可强行继续判分，可能得到低可信结果。

#### 7.4.2 具体落地方案

**统一输入框**

- 同一个输入框接收岗位链接、JD 文本和“链接 + JD”混合内容。
- 截图作为并列添加方式。
- 系统自动识别输入类型，不要求用户先选 Tab。

**智能切分**

- 明确分隔符 `---` 仍作为最高可信规则。
- 链接按行识别。
- 文本根据职位标题、岗位职责、任职要求等结构识别候选边界。
- 切分采用“规则优先、低置信度调用 LLM”：高置信规则结果直接进入确认页；边界不明确时才调用 LLM 返回候选切分，控制成本与等待时间。
- 识别结果进入确认页，不直接判分。

**多图 OCR**

- Phase 1 支持一次上传多张图片。
- 每张图片默认生成一份候选岗位。
- 若多张图片属于同一岗位，用户可在确认页选择并合并。
- 合并时保留图片来源顺序，合并后的 JD 仍可编辑。

**确认页**

每张岗位卡显示：

- 岗位名、公司、地区。
- 输入来源和原岗位链接。
- JD 完整度：完整、可能缺失、必须补全。
- 编辑、合并、拆分、删除。

**失败处理**

- 登录墙或反爬：保留链接，明确提示改用粘贴或截图。
- “必须补全”的岗位不能进入判分。
- 单条失败不阻塞其他岗位。
- 支持失败项单独重试。

#### 7.4.3 技术开发要求

- 增加统一导入解析接口，返回候选岗位数组和置信度，不直接写入正式匹配记录。
- 引入临时 `ingest_draft` 或等价结构，保存确认前数据和来源。
- 导入草稿支持一对多图片来源，并提供合并接口；合并操作要求幂等，不能重复拼接正文。
- 每个字段需保留来源：网页抽取、文本解析、OCR、用户修改。
- 用户修改后的字段优先级最高，后续解析不得静默覆盖。
- URL 规范化后去重；JD 使用规范化文本 hash 去重。
- “必须补全”的判定使用确定性规则，例如正文长度、职责/要求字段缺失，不仅依赖模型。
- OCR、URL 抽取和文本解析应按条目独立记录状态与错误码。
- 文本切分需返回 `confidence` 和 `split_method`（规则或 LLM），低置信度阈值通过配置管理。
- 单批继续限制在 20 个岗位；超过后引导拆批。

#### 7.4.4 验收标准

- 用户可以粘贴混合内容并得到可确认的岗位卡。
- 用户可以一次上传多张截图；默认一图一岗，并能在确认页合并属于同一岗位的图片。
- 单份含多个空行的 JD 不会仅因空行被拆分。
- 不完整岗位无法误进入判分。
- 用户修正字段后不会被后台结果覆盖。
- 导入失败项具有明确原因和下一步。

#### 7.4.5 产品边界

- 不做全站爬岗。
- 不绕过招聘网站登录、验证码和反爬限制。
- 不保证所有网页都能自动抽取。
- 不自动提交未经用户确认的岗位。
- 首期不做浏览器插件和系统级剪贴板常驻监听。

### 7.5 优化项三：行动导向的批量结果页

#### 7.5.1 为什么优化

当前每个结果同时提供星标、生成报告、打开详情和投递链接。功能完整，但操作权重相近，用户仍需自己决定下一步。结果页缺少批量处理能力，多岗场景下效率不足。

#### 7.5.2 具体落地方案

**结果排序**

默认按建议行动分组，再按分数排序：

1. 优先投递。
2. 修改后投递（所有“冲”档岗位统一进入此组）。
3. 补充信息后再判断。
4. 不建议投。
5. 判分失败。

允许切换为按分数、公司或导入顺序排序。

**结果行信息层级**

第一层：

- 岗位、公司、地区。
- 匹配分、保/稳/冲/不建议。
- 明确结论：“建议投”“修改后投”“不建议投”。

第二层：

- 最重要的 1–2 个缺口。
- 推荐简历名称。
- 推荐理由摘要。

操作区：

- 仅保留一个主按钮，由状态决定：“优化简历”“去投递”“查看报告”“补全信息”。
- 星标、换简历、查看详情、归档放入更多菜单。

**多选批量操作**

- 加入待改简历。
- 加入待投。
- 生成行动报告。
- 归档。

高成本操作在确认框中显示数量和预计行为，不显示虚假的精确完成时间。

**结果生成过程**

- 每行独立展示排队、解析、判分、成功和失败状态。
- 已完成结果立即可操作，不等待整批结束。
- 离开页面后任务继续，返回后恢复。

#### 7.5.3 技术开发要求

- 后端返回标准化中文 `recommended_action`，取值为：
  - `去投递`
  - `修改后投`
  - `补全信息`
  - `不建议投`
  - `重试`
- 首期由 Judge 分数、档位和信息完整度通过规则映射，不额外调用 LLM：
  - 导入内容不完整 → `补全信息`
  - 判分失败 → `重试`
  - 档位为“不建议” → `不建议投`
  - 档位为“冲” → `修改后投`
  - 档位为“保/稳” → `去投递`
- fatal 缺口不再强制覆盖分数档位。系统保留按分数计算出的“保/稳/冲/不建议”档位，同时以高显著性风险标识提示 fatal 缺口；行动区应提示用户先确认或处理该缺口。
- 新增批量状态更新接口，要求幂等，并返回逐条成功/失败结果。
- 批量生成报告只为用户选中的岗位创建任务。
- 批次需持久化，不依赖浏览器内存保存结果。
- 前端按 `batch_id` 恢复任务和结果。
- 星标保留，但不再作为生成报告的隐性前置条件。

#### 7.5.4 验收标准

- 用户无需进入详情即可判断岗位和执行推荐动作。
- 每行只有一个视觉主按钮。
- 多选操作支持部分成功，并明确失败条目。
- 刷新或重新登录后仍可恢复批次结果。
- 判分失败不影响已成功岗位。

#### 7.5.5 产品边界

- 不自动替用户归档或投递。
- 不默认对所有高分岗位生成报告。
- 不隐藏“不建议投”结果。
- 不把分数作为唯一判断依据；高分岗位出现 fatal 缺口时不强制降档，但必须突出标注，不能隐藏风险。

---

### 7.6 优化项四：从“匹配库”升级为“投递看板”

#### 7.6.1 为什么优化

“匹配库”强调数据存档和版本，对用户而言缺少行动含义。虽然当前已经支持投递状态筛选，但默认仍是岗位列表，用户无法一眼看到哪些岗位需要处理。

#### 7.6.2 具体落地方案

**一级名称**

- 用户侧统一改为“投递看板”。
- 内部数据结构仍可保留 jobs/matches 命名。

**默认视图**

按状态分组：

- 待决策。
- 待改简历。
- 待投。
- 已投。
- 面试中。
- 结束。

每组显示数量，并支持折叠。

**岗位卡片**

显示：

- 公司、岗位、地区。
- 最新分数与档位。
- 当前使用简历。
- 当前状态。
- 最后更新时间。
- 推荐下一步。

**状态变更**

- 支持卡片内快速变更状态。
- 点击原岗位链接后，仅建议进入“已投”，不得自动标记为已投。
- 进入“面试中”后显示“生成/查看面试准备”。
- “已结束”要求可选原因：岗位关闭、未通过、主动放弃、已拿 Offer、其他。

**保留能力**

- 公司、岗位、地区、招聘类型筛选继续保留。
- 公司视图降为二级入口。
- 历史版本放入岗位详情，不占列表主信息。

#### 7.6.3 技术开发要求

- 沿用现有枚举并增加“待决策”。数据库、接口和前端统一使用中文枚举值：
  - `待决策`
  - `待改简历`
  - `待投`
  - `已投`
  - `面试中`
  - `结束`
- 不增加独立的“已拿 Offer”状态；使用 `closed_reason=offer` 记录结束原因为拿到 Offer。
- 明确岗位状态允许流转，不允许写入枚举外的任意字符串。
- 为状态变化增加 `application_status_history` 或等价事件记录。
- 状态接口返回更新时间，处理并发覆盖。
- 看板接口支持按状态分组、筛选、排序和分页。
- 不能仅在前端完成分组；后端应返回各状态数量。
- 保留旧字段兼容迁移，避免已有岗位状态丢失。
- 结束原因与 Offer 结果为可选字段，首期不要求填写。

#### 7.6.4 验收标准

- 用户进入页面后能立即看到各阶段岗位数量。
- 从待改到待投、已投和面试中的流转不超过两次点击。
- 点击投递链接不会被错误记录为已投。
- 历史匹配版本仍可查看和重新匹配。
- 原有筛选功能不回退。

#### 7.6.5 产品边界

- 不做联系人、跟进记录、邮件同步等重型 CRM。
- 不自动读取 Boss 或招聘网站的真实投递状态。
- 不承诺岗位链接持续有效。
- 公司视图不升级为公司情报或岗位推荐系统。

---

### 7.7 优化项五：行动型报告

#### 7.7.1 为什么优化

当前报告以六个模块 Tab 展示，内容完整，但第一屏没有把用户最需要执行的动作收敛出来。用户必须阅读多个模块后自行归纳，增加了从报告到投递的距离。

#### 7.7.2 具体落地方案

**报告首页改为行动摘要**

第一屏固定展示：

1. 是否值得投及一句话原因。
2. 必须修改的 3 件事。
3. 建议补充的经历证据。
4. 最可能被问的 3 个面试问题。
5. 当前推荐下一步。

**行动按钮**

- “应用到简历草稿”：首期写入独立的“改写草稿箱”，保存建议内容供用户编辑和复制，不生成 DOCX，也不修改简历画像或原文件。
- “复制建议”：复制单条内容，不要求复制整份报告。
- “加入待投”：修改完成后进入待投状态。
- “开始面试准备”：进入针对本岗位的问答清单。

**详细报告**

- 原六模块完整保留，放入“查看分析依据”。
- 评分模型、匹配表和详细缺口作为解释层。
- 跨简历证据必须显示来源简历。

**任务完成反馈**

- 用户可勾选修改项“已处理”。
- 所有必须修改项处理后，提示进入待投，但不自动改变状态。

#### 7.7.3 技术开发要求

- 扩展报告输出或增加确定性转换层，生成统一 `action_summary`。
- 结构至少包括：
  - `decision`
  - `must_do_items`
  - `evidence_suggestions`
  - `interview_focus`
  - `next_action`
- 现有六模块字段保持兼容，避免历史报告无法展示。
- “应用到简历”首期必须创建独立草稿箱记录，不覆盖原始上传文件、简历画像或既有版本。
- 草稿记录至少包含：目标简历、来源岗位、来源报告、原文、建议文本、用户编辑文本和创建时间。
- 写回项需记录来源岗位、来源报告、原文和修改后文本。
- 跨简历内容继续保留 `source_resume`，没有可验证来源时不得输出为事实。
- 单条任务完成状态需持久化，刷新后保持。

#### 7.7.4 验收标准

- 用户打开报告第一屏即可看到结论和行动清单。
- 不查看六个详细模块也能完成简历修改和投递推进。
- 写回简历不会覆盖原版本。
- 跨简历证据均有来源标注。
- 历史报告仍能通过兼容层正常显示。

#### 7.7.5 产品边界

- 不直接修改用户原始 PDF/DOCX 文件。
- 不自动编造数据、职责或项目成果。
- 不自动将所有建议写回简历。
- 不弱化原六模块的质量标准。
- 首期不做完整在线简历排版编辑器。
- 首期不生成新的 DOCX/PDF；后续是否生成完整文件根据草稿箱使用率决定。

---

### 7.8 优化项六：可解释的简历推荐与即时纠错

#### 7.8.1 为什么优化

自动选简历已经存在，但“为什么推荐”和“换另一份会怎样”展示不足。对多方向用户而言，推荐错误不是普通误差，而是信任问题。

#### 7.8.2 具体落地方案

**推荐卡**

- 推荐主简历。
- 推荐理由：最多 3 条，必须对应 JD 要求和简历证据。
- 备选简历及主要差距。
- 展示方向标签是否匹配。

**用户纠错**

- “改用另一份简历”常驻可见。
- 修改后保留 JD、岗位元数据和原推荐结果。
- 询问可选原因：方向不对、版本过旧、经历不完整、其他。
- 用户可就地修改当前求职偏好，例如城市、目标方向或硬约束。

**比较范围**

- 全部已解析简历先执行低成本粗排，只有 Top 2 执行完整 Judge。
- 默认展示 Top 2 的真实 Judge 结果，不同时对所有简历做完整判分或报告。
- 需要时可展开全部简历的粗排结果。

#### 7.8.3 技术开发要求

- 推荐接口返回 Top 2、理由、证据引用和差异点。
- 推荐流程应优先复用 `resume_id + jd_hash` Judge 缓存；Top 2 可并行执行，避免串行等待。
- 接口先返回粗排推荐和任务状态；完整 Judge 超过前端等待阈值时异步完成，不阻塞用户编辑 JD 或浏览其他岗位。
- 推荐等待目标：有缓存时 P95 ≤ 1 秒；无缓存时首个可用推荐 P95 ≤ 5 秒，Top 2 完整比较允许后台继续更新。
- 推荐理由不得只返回泛化文本，需关联 `resume_id` 和 JD requirement。
- 保存推荐曝光、采纳、改选及改选原因。
- 用户改选后重新 Judge 时复用 JD 解析缓存。
- 推荐结果需记录模型/规则版本，便于回溯质量。
- 偏好更新不得 retroactively 静默修改历史判分。

#### 7.8.4 验收标准

- 用户能理解为什么推荐当前简历。
- 用户可在一次操作内换简历并继续。
- 换简历不会丢失输入内容。
- 产品能够统计推荐采纳率和改选原因。

#### 7.8.5 产品边界

- 推荐是建议，不强制替用户选择。
- 不承诺推荐简历一定获得最高面试率。
- 不因偏好不匹配直接篡改客观胜任力分数。
- 不为每份简历默认生成深报告。

---

### 7.9 优化项七：全链路埋点与反馈闭环

#### 7.9.1 为什么优化

v2 的目标是推动用户行动。如果只统计匹配次数、报告生成量和页面访问量，就无法判断优化是否真正减少了从决策到投递的摩擦。

#### 7.9.2 具体落地方案

建立以下主漏斗：

```text
开始导入
→ 导入确认
→ 判分完成
→ 保留高意向岗位
→ 执行简历修改/生成报告
→ 进入待投
→ 点击投递链接
→ 用户确认已投
→ 进入面试中
```

补充质量指标：

- 智能切分后合并/拆分率。
- 岗位字段人工修改率。
- 推荐简历采纳率和改选原因。
- “不建议投”后的归档/强行投递行为。
- 推荐下一步按钮点击率。
- 报告行动项完成率。

#### 7.9.3 技术开发要求

- 统一事件命名和公共字段：`user_id`、`session_id`、`job_id`、`match_id`、`batch_id`、`source`、`occurred_at`。
- 前端交互事件与后端成功事件分开记录，避免把点击当完成。
- 状态变化以服务端事件为准。
- 不在事件中写入完整 JD、简历正文或报告正文。
- 管理端增加 v2 漏斗、分阶段转化和异常率。
- 为历史事件保留兼容映射，不要求一次性重写旧数据。

#### 7.9.4 验收标准

- 可以按用户和批次还原完整主路径。
- 能区分“点击去投递”和“用户确认已投”。
- 能识别用户主要流失在导入、判分、改简历还是投递阶段。
- 埋点失败不阻塞用户主流程。

#### 7.9.5 产品边界

- 不收集招聘网站账号、聊天内容或未主动提交的数据。
- 不使用埋点内容训练模型，除非后续获得明确授权。
- 不把链接点击等同于投递成功。

---

### 7.10 横向技术要求

#### 7.10.1 状态与任务可靠性

- 批量解析、Judge 和报告任务状态以数据库为准。
- 前端刷新、重新登录或切换页面后可恢复。
- 任务接口必须幂等，重复请求不得创建重复报告或重复状态记录。
- 失败项支持单独重试，并保留可理解的错误原因。
- 中期将进程内后台线程迁移到可靠任务队列；若 v2 首期不迁移，至少加入启动恢复和超时补偿。

#### 7.10.2 性能

- 工作台和投递看板不触发 LLM。
- 列表和聚合接口 P95 ≤ 800ms。
- 用户确认导入后 300ms 内出现明确任务状态。
- 已完成的单条判分立即返回，不等待整批。
- 长列表必须分页或虚拟化，首期建议每页 20–50 条。

#### 7.10.3 数据兼容

- 现有 job、match_run、preference、resume 数据不得丢失。
- 新页面可直接读取历史岗位并映射到默认状态。
- 历史报告通过兼容转换生成行动摘要；无法转换时仍可查看原六模块。
- 所有迁移脚本应可重复运行，并在执行前备份数据库。

#### 7.10.4 安全与隐私

- 所有聚合、批量和状态接口必须校验当前用户所有权。
- 外部 URL 抓取需防范 SSRF，只允许 HTTP/HTTPS，并拦截内网、回环和云元数据地址。
- 展示外部链接时使用安全的新窗口参数。
- 简历和 JD 不进入前端日志或埋点正文。
- 上传文件继续限制类型和大小。

#### 7.10.5 可访问性与适配

- 主操作可通过键盘完成。
- 状态不能只依赖颜色表达。
- 异步状态使用可读文本并兼容屏幕阅读器。
- 桌面端为 v2 首发重点；移动端保证查看、状态推进和链接导入可用。

---

### 7.11 假设与待验证项

| 假设 | 验证方式 | 失败后的调整 |
|---|---|---|
| 工作台能降低用户寻找下一步的成本 | 首次决策时间、待办点击率、访谈 | 缩减工作台模块，只保留任务和导入 |
| 建议行动比分数排序更有用 | 两种排序的推进率对比 | 保留分数默认排序，建议行动作为筛选 |
| 用户愿意维护轻量投递状态 | 状态更新率和回访率 | 减少状态数，只保留待投/已投/面试 |
| 行动摘要能提高报告使用率 | 行动项点击率和完成率 | 调整摘要内容，不降低详细报告质量 |
| 推荐解释能提高采纳率 | 理由展开率、采纳率、改选原因 | 改为证据对比，减少自然语言解释 |

### 7.12 已确认的开发口径

以下事项不再作为待决问题，开发按此执行：

- 按 Phase 独立开发、验收和上线，不等待全部 v2 功能完成。
- v2 新导航直接替换旧导航，但保留现有页面能力和历史数据访问。
- Phase 1 建立批次持久化、刷新恢复和接口幂等；暂不引入 Redis/Celery。服务重启恢复与可靠队列按后续阶段实施。
- “冲”档统一推荐“修改后投”。
- fatal 缺口不强制降低按分数得出的档位，但必须突出标注风险。
- 投递状态沿用当前枚举并增加“待决策”；状态值在数据库、接口和前端统一使用中文。
- 不增加“已拿 Offer”状态，以 `closed_reason=offer` 记录。
- 简历写回首期使用独立改写草稿箱，不生成 DOCX/PDF。
- Phase 1 支持多图上传；一张图片默认一份候选岗位，确认页支持合并。
- 智能切分规则优先，仅在低置信度时调用 LLM。
- 全部简历先粗排，Top 2 执行真实 Judge；接受额外模型成本，但必须使用缓存、并行和异步更新控制等待时间。
- 工作台“今日进度”按用户时区自然日统计；未完成待办不受日期限制。
- 待办默认优先级：待补全/失败 → 报告完成待查看 → 待改简历 → 待投 → 已投待备面；同级按更新时间倒序。
- 打开原岗位链接不自动标记已投；用户返回产品后再询问是否完成投递。
- 不建议投的岗位不自动归档；允许用户覆盖系统建议，并记录覆盖行为。
- v2 Phase 1–3 继续兼容 SQLite，同时避免新增强绑定 SQLite 的实现。
- Phase 1 采集 v2 埋点，Phase 2 更新管理端漏斗展示。
- 桌面端完整交付；移动端首期保证工作台查看、链接导入、状态推进、原岗位跳转和行动摘要可用。

## 8. Release

### 8.1 排期原则

- 一个迭代按 2 周估算。
- 优先打通“进入产品 → 完成一个真实推进动作”。
- 每个阶段可独立上线和验证。
- 不等全部 v2 完成后一次性发布。

### 8.2 Phase 0：基线与设计准备（0.5 个迭代）

**目标：** 建立可比较的体验基线，确定统一信息架构。

**产品/设计**

- 完成工作台、统一导入、行动结果页和投递看板原型。
- 确认状态枚举、推荐行动规则和文案。
- 用 5 个真实求职任务进行可用性走查。

**开发**

- 补齐现有主漏斗埋点。
- 盘点数据库字段和历史数据迁移方案。
- 明确批次持久化和任务恢复方案。

**退出条件**

- 能获得 v1 的首次决策时间和判分后推进率基线。
- 核心页面原型通过评审。

### 8.3 Phase 1：主路径重构（1.5 个迭代）

**范围**

- 今日求职工作台。
- 统一导入入口和确认页。
- 导入完整度校验。
- 行动导向的批量结果页。
- 推荐下一步规则。
- 批次持久化与恢复。

**不包含**

- 简历写回。
- 完整投递看板重构。
- 面试任务清单。

**阶段成功标准**

- 用户可以从首页导入多个岗位并完成至少一个推进动作。
- 不完整岗位不会误判分。
- 批量结果刷新后可恢复。

### 8.4 Phase 2：投递推进闭环（1 个迭代）

**范围**

- 匹配库更名并重构为投递看板。
- 状态分组、流转历史和结束原因。
- 批量加入待改、待投、归档。
- 工作台待办与看板状态联动。
- v2 主漏斗管理端看板。

**阶段成功标准**

- 高意向岗位可顺畅进入待改、待投、已投和面试中。
- 工作台能够根据状态生成正确待办。
- 可以计算高意向岗位推进完成率。

### 8.5 Phase 3：行动报告与顾问信任（1–1.5 个迭代）

**范围**

- 报告行动摘要。
- 行动项完成状态。
- 单条复制和应用到简历草稿。
- Top 2 简历推荐解释。
- 推荐改选原因。
- 面试准备任务入口。

**阶段成功标准**

- 报告用户无需阅读全部模块也能完成修改和推进。
- 推荐简历采纳与改选原因可衡量。
- 写回不会覆盖原始简历。

### 8.6 Phase 4：稳定性和增强（按数据决定）

候选事项：

- 可靠任务队列和 SSE 状态更新。
- 移动端快速追加岗位。
- 高频招聘站点适配增强。
- 投递状态轻提醒。
- 行动规则个性化。

只有在 Phase 1–3 指标验证后才进入排期。

### 8.7 明确不进入 v2 的事项

- 自建岗位市场和主动岗位推荐。
- 自动代投、代聊或招聘网站账号接管。
- 重型 CRM、联系人和日历系统。
- 公司情报数据库。
- 完整在线简历排版编辑器。
- 情绪陪伴型聊天助手。
- 为提升指标而降低“不建议投”比例。

### 8.8 上线策略

1. 先对内部和少量测试用户开放。
2. 观察导入错误率、任务失败率和历史数据兼容性。
3. 工作台与旧首页保留短期开关，出现严重问题可回退。
4. 投递看板上线时保留旧列表视图一个版本。
5. 每个 Phase 上线后至少观察一个完整使用周期，再决定下一阶段细节。

### 8.9 最终验收清单

- [ ] 用户登录后能看到明确的下一步。
- [ ] 用户可在统一入口导入链接、文本或截图。
- [ ] 不完整岗位不会进入正式判分。
- [ ] 批量结果每行只有一个主行动。
- [ ] 批量任务刷新后可恢复。
- [ ] 高意向岗位能进入完整投递状态链路。
- [ ] 点击投递链接不等于已投。
- [ ] 报告第一屏提供行动清单。
- [ ] 简历推荐有理由、备选和纠错入口。
- [ ] 简历写回不覆盖原始文件。
- [ ] 跨简历证据有来源且不编造。
- [ ] v2 主漏斗可以完整统计。
- [ ] 普通用户看不到管理端入口。
- [ ] 旧岗位、旧报告和旧状态均可继续访问。

## 9. 一页结论

OfferOS v2 的重点不是增加更多 AI 功能，而是让现有能力围绕一次真实求职行动重新组织：

```text
首页告诉用户做什么
→ 导入不要求学习规则
→ 判分结果直接给出下一步
→ 投递看板持续推进
→ 报告变成可执行清单
→ 推荐有解释且可以纠错
```

v2 的成功不是“生成了更多报告”，而是用户能用更少判断成本，把真正值得投的岗位推进到投递和面试。
