# 批量匹配交互流（深挖草案）

> 状态：**探索稿** — 非本期提速执行范围；提速方案确认落地后再评审本草案  
> 目标：求职期间更快了解公司与匹配岗位，先批量决策，再按需深报告（质量不降）

---

## 1. 要解决的用户问题

| 现在 | 求职真实节奏 |
|---|---|
| 一次粘贴/截图 → 一个 JD | 一周盯多家公司、每家多岗 |
| 每次完整走解析→判分→长报告 | 多数岗只需「该不该投」 |
| 效率瓶颈在输入与等待 | 瓶颈应在「筛选」而非「写报告」 |

产品命题：**先用批量判分榜完成筛选，再用高质量报告打赢少数高意向岗。**

---

## 2. 信息架构：三层

```
公司（可选）
  └── 岗位批次 Batch（一次丢入的 N 个 JD）
        └── 匹配结果行（简历 × 岗位）
              ├── 快结果：分数 / 档位 / 一句话 / 致命缺口
              └── 深结果：完整 Action 报告（按需或自动 Top-K）
```

单岗流程仍保留，作为「深耕入口」；批量是「筛选入口」。

---

## 3. 核心用户故事

1. **作为求职者**，我想一次粘贴多段 JD 或上传多张截图，以便晚上快速刷完今日岗位。  
2. **作为求职者**，我想按匹配分排序看榜，以便 1 分钟内决定哪 2–3 个值得深挖。  
3. **作为求职者**，我想对星标/高分岗一键生成完整行动报告，以便改简历和备面（质量与单岗一致）。  
4. **作为求职者**，我想按公司聚合查看，以便理解「这家公司哪个方向更适合我」。  
5. **作为求职者**，批量跑的时候我想去干别的，回匹配库能看到每条进度。

---

## 4. 主交互流（推荐）

### 4.1 入口

- 匹配库 / 导航增加：**批量匹配**（与「单岗匹配」并列）。  
- 单岗向导保留；高级用户从批量进，新手可仍走单岗。

### 4.2 步骤流

```
Step A  选简历画像（必须已解析）
        │
Step B  添加岗位（支持组合）
        │  · 批量粘贴：用 --- 或空行分隔多段 JD
        │  · 多图上传：队列 OCR，逐条回填可编辑卡片
        │  ·（中期）公司名 / 招聘页链接
        │
Step C  预览岗位卡片列表（可删、可改标题/文本、可标公司名）
        │  每张卡：标题猜测 | 文本摘要 | 编辑 | 移除
        │
Step D  开始批量判分（只跑 JD 解析 + Judge，默认不跑全量 Action）
        │  进度：已完成 3/10 · 可后台运行
        │
Step E  匹配榜（主画面）
        │  排序：分数 | 档位 | 公司
        │  筛选：保/稳/冲/不建议 | 仅致命缺口 | 某公司
        │  行操作：星标 | 生成深报告 | 打开单岗详情 | 忽略
        │
Step F  深耕
          对星标或「生成报告」的岗 → 复用提速方案的异步高质量报告
```

### 4.3 匹配榜行信息架构（快决策）

每行固定展示（一屏可扫）：

| 字段 | 作用 |
|---|---|
| 岗位标题 / 公司（可空） | 识别 |
| 档位徽章 + 综合分 | 主决策 |
| 一句话结论 | 理由摘要 |
| 致命/重要缺口（最多 2 条） | 风险 |
| 状态 | 判分中 / 已判分 / 报告生成中 / 报告就绪 |
| 操作 | 星标、生成报告、详情 |

**禁止**在榜上展开完整六模块——避免信息过载，也避免暗示「批量=浅质量报告」。

### 4.4 深报告触发规则（保质）

| 触发 | 行为 |
|---|---|
| 用户点击「生成行动报告」 | 按现行质量契约异步生成 |
| 用户星标 | 可选：自动排队生成（设置项） |
| 批量结束后自动 | 仅 Top 1–3 分或「稳/冲」自动生成（可关） |
| 默认批量 | **只判分**，控制成本与时延 |

深报告 = 与单岗同一套 Action 标准，不另做缩水版。

## 5. 关键路径详述

### 路径 1：今晚 Boss 海刷（高频）

1. 打开批量匹配 → 选简历  
2. 粘贴 8 段 JD（或 8 张图）→ 预览删掉 1 个无关岗  
3. 点「开始判分」→ 去改另一份简历 / 切走  
4. 通知或回匹配库：8 条判分完成  
5. 榜上筛「稳+冲」得 3 条 → 星标 2 条 → 生成报告  
6. 明日投递前打开报告改 bullet  

**成功标准**：30 分钟内完成「8 评 2 深」，且 2 份报告质量不降。

### 路径 2：盯一家目标公司

1. 创建/选择公司「示例科技」  
2. 导入该公司 5 个相关 JD  
3. 榜按分排序 + 公司筛选  
4. 看哪条业务线更匹配 → 对 Top 岗深报告  
5. 公司卡沉淀：常见 must_have、我的相对强弱  

**成功标准**：用户能回答「这家公司我该攻哪个岗」，而不仅是「这个 JD 多少分」。

### 路径 3：已有单岗结果升级批量

- 匹配库支持「加入新一批」挂到同一公司下。  
- 历史单岗 run 可被公司视图收纳（弱绑定即可）。

## 6. 状态与等待体验（与提速方案对齐）

批量中每一行独立状态机（复用单岗解耦）：

```
queued → parsing_jd → judging → judged
                         └→ report_pending → report_done（仅触发时）
```

- 整批进度条 + 行内状态  
- 允许取消未开始的行；已判分保留  
- 失败行可单独重试（解析失败 / 判分失败分离）

---

## 7. 边界与规则

| 议题 | 建议 |
|---|---|
| 单批上限 | 首期 10–20 岗，防止滥用与超时 |
| 超长 JD | 与单岗同样截断策略，卡片上提示 |
| 重复 JD | hash 去重，提示「与第 x 条重复」 |
| 无公司名 | 允许；公司为增强而非必填 |
| 与单岗关系 | 榜上行「打开」进入与单岗一致的详情/报告页 |

## 9. 与提速方案的依赖

| 依赖 | 原因 |
|---|---|
| Judge/Report 解耦 | 批量只能跑 Judge；否则 N 份长报告不可用 |
| 异步状态 + 匹配库进度 | 批量必然后台化 |
| 报告质量契约不变 | 深耕岗与单岗体验一致，品牌不裂 |

**结论：先落地提速解耦，再做批量；批量是提速方案在「多岗」上的自然延伸。**
