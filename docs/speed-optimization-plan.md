# OfferOS 提速优化方案（质量不降级）

> 状态：**P0 + P1 已落地**  
> 确认项：1) P0 仅解耦+异步，模块编排→P1 2) 判分后自动生成报告 3) 方案 B 改造 `/match/run` 早返回 4) 轮询  
> P1：JD/判分/报告缓存 · OCR 异步 · Action 四模块并行编排 · must_haves 覆盖校验 · 模块进度 UI  
> 约束：提速不得牺牲现有报告质量标准（Action Agent 质量契约保持）  
> 范围：单岗匹配主链路；批量匹配见 `docs/batch-match-interaction.md`

---

## 1. 背景与目标

### 1.1 现状

当前单岗路径大致为：

```
截图 OCR（可选，同步）
  → JD 解析（同步，用户等待）
  → /match/run：Judge + Action 串行（同步，用户等待）
  → 一次展示判分 + 完整报告
```

报告质量已通过强化 Action prompt 明显提升（结论结构、匹配表覆盖、改写 3–5、面试 6–10 等），但单次 Action 输出变大，**判分被报告拖慢**，用户在每一步都需干等完整结果。

### 1.2 目标

| 目标 | 说明 |
|---|---|
| 决策快 | 「综合判分 / 该不该投」成为主路径首个可消费结果 |
| 等待可拆 | 用户不必在 JD 解析、判分、报告每一步都阻塞到结束 |
| 质量不降 | Action 各模块质量标准、字段完整度、覆盖率要求不降低 |
| 可度量 | 有明确前后指标，防止用「变浅」换「变快」 |

### 1.3 非目标（本期不做）

- 批量多岗匹配交互与能力（另案）
- 更换模型供应商 / 大规模调参实验平台
- 为提速缩短报告字数、减少面试题、抽样 must_haves

## 2. 问题拆解

### 2.1 真实耗时

| 环节 | 当前形态 | 对用户阻塞 |
|---|---|---|
| 简历解析 | 上传同步 LLM | 仅首次；画像可复用 |
| JD 截图 OCR | 同步 vision | 堵在输入步 |
| JD 解析 | 同步 LLM，完成才能点判分 | 堵在步骤 1 |
| Judge | 与 Action 同请求串行 | 被报告拖长 |
| Action | 超大 JSON，质量主力 | 最长；与决策捆死 |

### 2.2 感知耗时

- 判分页长期停在「判分中…」，无子阶段
- 报告未就绪前用户无法先做「投/不投」决策并离开
- 假进度无法区分「还在算」与「已失败」

### 2.3 根因一句话

**质量标准变重是对的；错在把「决策结果」和「深度报告」绑在同一次同步等待里。**

---

## 3. 设计原则

1. **质量用架构保住，速度用节奏优化** — 不砍 prompt 规格，改「何时算、何时展示」。
2. **主路径只阻塞决策** — 用户为「该不该投」等待；深度内容可后到。
3. **深度按模块交付，标准不降** — 分模块生成时，每模块仍满足现有质量契约。
4. **真进度替代假进度** — 服务端阶段可观测。
5. **缓存消灭重复等待** — 同简历 / 同 JD / 同匹配对不重复计费等待。

## 4. 方案总览

```
┌─────────────────────────────────────────────────────────┐
│  P0  判分与报告解耦 + 先展示决策 + 报告异步/分模块        │
│  P0  真阶段状态（判分完成 / 报告生成中 / 模块就绪）        │
│  P1  JD/OCR 不堵主路径；简历·JD·判分缓存                  │

│  P2  模型路由（抽取快 / 报告强）；按需触发深报告           │
└─────────────────────────────────────────────────────────┘
```

## 5. P0：决策与报告解耦（本期核心）

### 5.1 产品行为

用户点击「综合判分」后：

1. **尽快返回并展示**：档位、综合分、三维分数、one_liner、strengths、gaps（Judge 结果）。
2. 此时即可：保存到匹配库、标记意向、进入下一岗、或打开报告页看「生成中」。
3. **后台继续**生成完整 Action 报告（质量标准与现行一致）。
4. 报告模块就绪后：匹配库/报告页自动或手动刷新为完整内容；支持「报告生成失败 → 仅重试报告」。

### 5.2 接口形态（建议）

**方案 A（推荐，改动清晰）**

| 接口 | 职责 | 用户等待 |
|---|---|---|
| `POST /api/match/judge` | 只跑 Judge，写入 match_run（report 状态 = pending） | 短 |
| `POST /api/match/{run_id}/report` 或自动 enqueue | 只跑 Action，更新 report_json | 不阻塞判分页 |
| `GET /api/match/{run_id}` | 轮询/查询状态与已就绪模块 | 非阻塞 |

**方案 B（兼容现有 `/match/run`）**

- `/match/run` 改为：完成 Judge 即返回；服务端 BackgroundTask 继续 Action。
- 前端判分页立刻渲染；报告页/匹配库显示 `report_status`。

推荐 **A 或 B 择一**；实现时以「Judge 返回与 Action 完成时间戳可分离」为准。

### 5.3 状态机

```
match_run:
  judge_status:  pending → running → done | failed
  report_status: idle → pending → running → done | failed

模块级（可选，P0.5）：
  modules: {
    conclusion: pending|done,
    match_table: pending|done,
    rewrite: pending|done,
    interview: pending|done
  }
```

### 5.4 前端逻辑链（单岗）

```
选简历（已解析 → 0 等待）
  → 确认 JD 文本
  → [可选] 后台 OCR，文本框可先编辑
  → JD 解析：可展示「解析中」，但允许「跳过预览直接判分」若已有可解析文本（P1）
  → 点判分 → 仅等 Judge → 展示决策卡
  → 报告 Tab：骨架屏 + 模块就绪亮起
  → 全程可离开；回匹配库看进度
```

### 5.5 质量保障（P0 硬约束）

- Action 仍使用当前质量契约（字数、条数、覆盖、禁止编造等）。
- 禁止用 mock 报告冒充「已完成」的正式结果；mock 仅作 LLM 失败 fallback，并在 UI 标注。
- Judge 结果一旦展示，报告不得改分（与现设计一致）。

## 6. P1：减少堵点与重复计算

### 6.1 OCR / JD 解析不堵决策

| 改动 | 说明 |
|---|---|
| OCR 异步 | 上传截图后立即可编辑空/旧文本；识别结果回填，不强制同步等待才能点「开始」 |
| JD 解析与判分策略 | 默认：解析完成再判分（准）。加速选项：对已粘贴长文本可「解析+判分」流水线化，解析结果供报告使用 |
| 复用 jd_profile | 已有（run 传 jd_profile）；UI 明确「未改 JD 则不重解析」 |

### 6.2 缓存策略（质量无损）

| Key | 缓存内容 | 失效 |
|---|---|---|
| resume_id | profile（已有库表） | 用户点「重新解析」 |
| hash(jd_text) | jd_profile | 文本变更 |
| resume_id + jd_hash | judge 结果 | 用户点「重新判分」 |
| match_run_id | report | 用户点「重新生成报告」 |

### 6.3 Action 模块编排（保质提速）

将一次超大 `complete_json` 拆为模块调用，**每模块 prompt 仍含对应质量标准**：

| 模块 | 输入 | 并行 | 校验 |
|---|---|---|---|
| M1 结论 + score_narrative | judge + profiles | 判分后立即 | 字数/结构 |
| M2 匹配表 + gaps/strengths | judge + jd must_haves | 与 M1 并行 | must_haves 覆盖率 |
| M3 简历改写 | gaps + evidence | 可等 M2 缺口列表 | 条数 3–5 |
| M4 面试包 | gaps + evidence | 与 M3 并行 | 题量 6–10、字段齐全 |

墙钟时间 ≈ max(M1,M2) + max(M3,M4)，总信息量与现网一致或更高。  
失败策略：单模块重试；已完成模块保留。

> 若 P0 只做「整包 Action 异步」已明显改善体感，模块编排可作为 P1 增强，避免一次改太大。

## 7. P2：模型与算力策略（可选）

| 任务 | 策略 |
|---|---|
| OCR / JD 结构化 | 更快模型、短输出 |
| Judge | 中快模型 + 现有本地加权/档位修正 |
| Action 各模块 | 维持强模型，保证文案质量 |
| 深报告触发 | 默认判分后自动生成（体验完整）；后续可加「仅星标岗生成」开关省成本 |

本期不以换模型为必选项；优先解耦与异步。

## 8. 用户体验规格

### 8.1 判分页（决策页）

- 主按钮文案侧重「快速判断该不该投」。
- 展示完成即视为「本步成功」，不依赖报告。
- 文案示例：「判分完成 · 详细行动报告生成中」。

### 8.2 报告页

- 未就绪：分模块骨架 + 进度（如 2/4 模块完成）。
- 就绪：与当前高质量报告一致的信息架构与字段。
- 支持「重新生成报告」（不重跑 Judge，除非用户显式重判）。

### 8.3 匹配库

- 列表字段增加：`判分完成` / `报告生成中` / `报告就绪` / `报告失败`。
- 允许在报告未完成时打开岗位，查看已出判分。

### 8.4 错误与超时

- Judge 失败：明确可重试，不进入报告。
- 报告失败：保留判分，提供「只重试报告」。
- 超时提示区分环节，避免「全部失败」误导。

## 10. 验收标准

### 10.1 速度（体感与指标）

| 指标 | 验收 |
|---|---|
| Time-to-Decision | 点击判分 → 看到档位/分数，显著短于「等完整报告」的旧路径 |
| 判分页可离开 | 报告未完成时，判分结果已保存且可回看 |
| 无虚假完成 | 报告 status=done 前，不展示为「完整报告已生成」 |

### 10.2 质量（不降级）

对同一组「简历 × JD」抽样对比（解耦前后）：

| 检查项 | 标准 |
|---|---|
| conclusion / conclusion_structured | 结构完整，verdict 与 level 一致 |
| match_table | 覆盖 must_haves；弱/缺失有 gap_note |
| resume_rewrite | 3–5 条，含改写与 why_better |
| interview | ≥6 题，含 framework / sample_outline / followups |
| 编造 | 无简历未出现的硬事实 |

质量评分不低于改 prompt 后的当前水平（可用人工 1–5 分盲评）。

### 10.3 稳定性

- Judge 成功 + Report 失败：用户仍能看到决策，且可重试报告。
- 刷新页面：能从匹配库恢复判分；报告按状态继续展示或续跑。

## 11. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 异步任务在单进程 FastAPI 下不够稳 | P0 可用 BackgroundTasks + DB 状态；后续再上队列 |
| 模块拆分后拼接不一致 | 统一 judge 快照入各模块；禁止模块改分 |
| 轮询压力 | 间隔 1.5–2s；done/failed 停止；匹配库列表带状态减少空轮询 |
| 用户误以为报告变少 | 文案强调「生成中」而非「精简版」 |
